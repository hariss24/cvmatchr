# Constat — sécurité au 2026-08-08

**Mesuré par :** lecture directe du code serveur (`web/src/middleware.ts`,
`web/src/app/api/**/route.ts`, `web/src/lib/scraper/`, `web/src/lib/jobs/logos.ts`),
`grep` exhaustif pour chaque affirmation de manque, `npm audit --production` dans `web/`.
Aucun test n'a été exécuté contre une instance réellement déployée : les scénarios
d'exploitation ci-dessous sont des reproductions **par le code**, pas des attaques
lancées en conditions réelles.

## Mesures

### 1. SSRF non protégée dans `/api/jobs/logos`

La route accepte un tableau `companies` (chaînes libres, jusqu'à 120, aucune validation
au-delà de `typeof === "string"`) et le transmet à `logoUrlsFor` :

```
web/src/app/api/jobs/logos/route.ts:34-44
  const brut = (body as { companies?: unknown })?.companies;
  ...
  const companies = [...new Set(brut.filter(...))].slice(0, MAX_ENTREPRISES);
  const logos = await logoUrlsFor(companies, process.env.BRANDFETCH_CLIENT_ID);
```

`logoUrlsFor` → `resolveDomain` → `domainCandidates(company)` accepte **tel quel** tout
nom d'entreprise qui ressemble à un domaine :

```
web/src/lib/jobs/logos.ts:132-148 (domainCandidates)
  if (/^[a-z0-9-]+\.[a-z]{2,}$/.test(brut)) out.push(brut);
```

Le filtre qui suit (`recevable = tldPlausible(d) && domaineProche(d, company)`,
`logos.ts:257`) ne protège de rien quand `company` **est** le domaine soumis : envoyer
`company = "mon-domaine-attaquant.io"` produit `domaineProche("mon-domaine-attaquant.io",
"mon-domaine-attaquant.io") = true` (le nom normalisé est un préfixe de lui-même) et
`tldPlausible` accepte `.io` (`TLD_ACCEPTES`, `logos.ts:76`, huit extensions dont `.io`,
`.com`, `.co`, `.net`, `.org`, `.eu`, `.work`, `.agency`, `.group`, `.paris`, `.bzh`).
Le candidat passe alors à `siteConfirme` → `fetchAccueil` :

```
web/src/lib/jobs/logos.ts:196-204
  async function fetchAccueil(domain: string, signal: AbortSignal): Promise<string> {
    const res = await fetch(`https://${domain}`, { ... });
```

**Aucun garde-fou SSRF n'entoure cet appel** — `grep -rn "validateUrlForScraping"
web/src/lib/jobs/logos.ts web/src/app/api/jobs/logos/` : **0 correspondance**. Le fetch
part quel que soit le résultat final de `siteConfirme` (la requête réseau a déjà eu lieu
avant que le titre de la page soit comparé) : il suffit qu'un attaquant possède un
domaine dans une des huit extensions acceptées — n'importe lequel, y compris un `.io`
gratuit ou déjà possédé — et pointe son enregistrement DNS `A` vers une IP interne
(`169.254.169.254`, service interne du réseau du déploiement, etc.) pour faire émettre
au serveur une requête HTTP vers cette IP, à la demande. Reproduction par requête :
`POST /api/jobs/logos` avec `{"companies": ["mon-domaine-attaquant.io"]}`. La route
tourne en `runtime = "nodejs"` (`route.ts:5`), donc côté serveur, pas dans le navigateur
du candidat.

À comparer avec `/api/extract-job`, qui scrape aussi une URL fournie par l'utilisateur
mais **appelle bien** `validateUrlForScraping` avant tout `fetch` (`extract-job/route.ts`
→ `scraper.ts:29`) : le garde-fou existe dans le produit, il n'a simplement pas été
répliqué sur ce second chemin de fetch serveur piloté par l'utilisateur.

### 2. La protection SSRF existante (`ssrf.ts`) ne résiste pas au DNS rebinding

`validateUrlForScraping` (`web/src/lib/scraper/ssrf.ts:63-98`) résout le nom d'hôte par
`dns.lookup`, vérifie que l'IP obtenue n'est pas privée, puis renvoie **l'URL textuelle
d'origine** (`parsed.toString()`), hostname inclus — pas l'IP validée. `scraper.ts:42-51`
appelle ensuite `fetch(currentUrl, ...)` sur ce même hostname : `fetch`/`undici`
effectuent leur **propre** résolution DNS au moment de la connexion, indépendante de
celle déjà faite pour la validation. Rien n'épingle la connexion à l'IP contrôlée.

Un attaquant qui contrôle son serveur DNS peut répondre une IP publique au premier
lookup (validation acceptée) puis une IP privée au second (celui que fait `fetch`,
quelques millisecondes plus tard) — c'est le schéma classique de contournement SSRF par
DNS rebinding. `web/src/lib/scraper/ssrf.test.ts` (52 lignes, 8 cas) ne couvre que la
validation elle-même (IP privée immédiatement renvoyée par le mock `dns.lookup`) ;
aucun cas ne simule deux résolutions différentes pour le même hostname. Le garde-fou
protège donc contre une IP privée statique, pas contre un hostname dont la résolution
change entre la validation et l'usage.

### 4. Authentification par jeton statique

`middleware.ts:31-45` et `api/login/route.ts:41-45` : le jeton de session posé dans le
cookie `auth_token` est le **SHA-256 du mot de passe partagé lui-même**, sans aléa ni
horodatage — `SHA256(REMOTE_AUTH_PASSWORD)`, identique pour toute session, toute
personne, à chaque connexion. Conséquences vérifiées par lecture du code :

- **Non révocable individuellement.** Le cookie est valable 30 jours
  (`maxAge: 30 * 24 * 60 * 60`, `login/route.ts:53`) ; le seul moyen de l'invalider est
  de changer `REMOTE_AUTH_PASSWORD`, ce qui déconnecte alors **tout le monde** à la
  fois — impossible de révoquer une seule session compromise.
- **Un jeton dérobé vaut le mot de passe.** Le jeton n'est pas un secret dérivé
  d'un aléa serveur : c'est une fonction pure du mot de passe. Le récupérer (poste
  partagé, export de cookies, extension de navigateur compromise) donne un accès de 30
  jours sans jamais connaître le mot de passe en clair.
- **Comparaison non constante en temps** (`middleware.ts:39`, `token !== expectedToken`
  sur une chaîne hexadécimale) : canal de timing théorique, impact pratique faible sur
  une comparaison réseau (le bruit réseau domine largement 64 caractères hex), mais
  contraire à la pratique standard (`crypto.timingSafeEqual`) pour peu de coût.

### 5. Rate limiting du login en mémoire de process

`api/login/route.ts:3` : `const rateLimits = new Map<string, ...>()`, au niveau module.
`web/src/app/layout.tsx:6` importe `@vercel/analytics`, signal (non certifiant à lui
seul, mais concordant) d'un déploiement Vercel — plateforme à fonctions serverless
multi-instances. Une `Map` en mémoire de process ne survit pas à un redémarrage de
fonction et n'est **pas partagée entre instances concurrentes** : le seuil annoncé de 5
tentatives/minute par IP (`route.ts:13`) ne s'applique qu'à l'instance qui a reçu la
requête, pas à l'ensemble du déploiement. Sur une plateforme qui répartit les requêtes
entre plusieurs instances chaudes, le vrai plafond effectif est un multiple non maîtrisé
de 5/minute. Non vérifié en conditions réelles (accès à l'infra de déploiement hors
périmètre de l'Éclaireur) — signalé comme hypothèse forte, pas comme mesure directe.

### 6. Content-Security-Policy minimal

`next.config.ts:26-30` : le seul en-tête `Content-Security-Policy` posé est
`frame-ancestors 'self';` — protège contre le clickjacking, ne restreint ni
`script-src`, ni `connect-src`, ni `object-src`. `X-Content-Type-Options: nosniff` et
`Strict-Transport-Security` sont bien présents (`next.config.ts:20-25`), mais un CSP
sans `script-src` n'apporte aucune défense en profondeur contre une XSS future — deux
`dangerouslySetInnerHTML` existent déjà dans le code (`layout.tsx:38`,
`JobCard.tsx:40`), tous deux sur du contenu statique aujourd'hui, mais rien ne
bloquerait l'exécution d'un script injecté si l'un d'eux venait un jour à recevoir une
donnée dynamique.

## Ce que fait la concurrence sur ce point

- **Rezi** (`rezi.ai/legal`, consulté le 08/08/2026 par récupération de page) : badge
  « AICPA SOC 2 Certified » affiché en bas de page. Aucun détail technique
  (chiffrement, 2FA, gestion des accès) n'est développé sur cette page précise — le
  badge est la seule preuve publique trouvée à ce niveau de profondeur.
- **Jobscan** (`jobscan.co/privacy`, recherche + tentative de récupération le
  08/08/2026) : la page de confidentialité affiche des badges de conformité
  d'accessibilité (« WCAG 2.1 AA », « ADA ») mais aucun badge ni mention de sécurité
  technique n'a pu être extrait de la page elle-même ; un résultat de recherche
  indépendant (non vérifié directement sur la page) évoque des « procédures physiques,
  électroniques et de gestion » génériques et un stockage via Salesforce, sans détail
  vérifiable de première main.
- **Teal** (recherche du 08/08/2026, page `tealhq.com/privacy-policy` inaccessible en
  lecture directe — 403) : un résultat de recherche indépendant évoque un chiffrement
  des données en transit et au repos, non vérifié de première main faute d'accès à la
  page elle-même — à traiter comme non confirmé.

Aucun des trois n'expose de détail vérifiable sur un mécanisme équivalent à une
protection SSRF ou à un modèle de session — ce n'est pas le genre d'information qu'un
produit publie sur sa page marketing. La seule comparaison directement mesurable est
la présence d'un badge de certification tierce (SOC 2, Rezi) qu'aucun concurrent ne
dément et que CVMatchr n'a pas d'équivalent à afficher — mais cette absence ne dit rien
en soi des vulnérabilités concrètes trouvées ci-dessus, qui elles sont vérifiées dans le
code et non par comparaison.

## Écart au seuil de `MISSION.md`

`MISSION.md` ne nomme aucun seuil de sécurité chiffré (contrairement à l'accessibilité
ou à la performance) — le point 1 (SSRF non protégée) et le point 3 (dépendances à CVE
haute sévérité, dont une RCE navigateur sur un chemin central du produit) sont
néanmoins des manques par nature, comparables à un dépassement de seuil « de facto » :
une brèche exploitable ne se mesure pas en millisecondes mais casse la promesse de
fiabilité du produit aussi sûrement qu'un temps de chargement dépassé. Le point 5
(rate limiting) touche indirectement au seuil « coût des appels externes » déjà nommé
dans `MISSION.md`, en ce qu'un brute-force du mot de passe partagé donnerait accès à
tous les appels IA facturés de l'instance.

## Écart à la concurrence

Non mesurable par nature (voir section précédente) : les manques trouvés ici sont des
défauts internes au code de CVMatchr, pas des capacités absentes que la concurrence
offrirait et que CVMatchr n'offrirait pas. Le seul point de comparaison publique
obtenu (badge SOC 2 chez Rezi, absent chez CVMatchr) est un signal de confiance
commerciale, pas une preuve technique.

## Chantiers proposés

1. **Protéger `/api/jobs/logos` contre le SSRF** — appliquer `validateUrlForScraping`
   (ou un garde-fou équivalent) avant tout `fetch(`https://${domain}`)` dans
   `logos.ts`, exactement comme le fait déjà `/api/extract-job`. Gain attendu : ferme
   une SSRF serveur reproductible en une requête, sur une route qui n'exige aucun
   privilège particulier au-delà du mot de passe partagé de l'app.
2. **Épingler la connexion SSRF à l'IP déjà validée** dans `scraper.ts`/`ssrf.ts`, pour
   fermer le contournement par DNS rebinding décrit au point 2 (ex. résoudre une fois,
   forcer `fetch`/l'agent HTTP à se connecter à l'IP validée tout en gardant le Host
   d'origine pour SNI/TLS). Gain attendu : la seule protection SSRF existante du produit
   devient réellement contraignante, pas seulement contre les URL statiquement privées.
3. **Mettre à jour les dépendances vulnérables** listées au point 3, en commençant par
   celles corrigibles sans changement de version majeure (`npm audit fix` :
   `pdfjs-dist`, `dompurify`, `nanoid`, `protobufjs`, `undici`), puis trancher pour
   `next`/`postcss`/`sharp` (nécessite `next@16.3.0`, hors plage déclarée
   actuellement — décision à soumettre au propriétaire vu l'ampleur du saut de
   version). Gain attendu : ferme 9 vulnérabilités connues dont une RCE navigateur sur
   le chemin d'import PDF, une fonctionnalité centrale du produit.
4. **Remplacer le jeton d'authentification statique** par un jeton de session aléatoire,
   horodaté et révocable indépendamment du mot de passe partagé, comparé en temps
   constant. Gain attendu : un jeton dérobé ne vaut plus un accès de 30 jours équivalent
   au mot de passe ; une session compromise devient révocable sans déconnecter tout le
   monde.
5. **Vérifier le rate limiting du login en conditions de déploiement réelles**, et le
   déplacer vers un stockage partagé entre instances si le déploiement est bien
   multi-instance (à confirmer avec le propriétaire, qui a accès à l'infra). Gain
   attendu : le seuil de 5 tentatives/minute annoncé redevient réellement opposable.
6. **Étoffer le CSP** au-delà de `frame-ancestors 'self'` (au minimum `script-src`,
   `connect-src`, `object-src`). Gain attendu : défense en profondeur si une future
   régression introduit une XSS sur l'un des deux `dangerouslySetInnerHTML` déjà
   présents ou sur un nouveau composant — non chiffrable directement, mais standard du
   secteur et coût de mise en œuvre faible.
